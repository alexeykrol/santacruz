# Правило: Работа с GitHub

*Согласовано с Алексеем Кролом (владелец репозитория) 2026-08-03. Отменяет прежнюю схему через промежуточную ветку `episodes`.*

## Принцип

**Одна задача — одна временная ветка — один PR непосредственно в `main`.**

Промежуточных веток нет. Ветка живёт ровно столько, сколько живёт её PR.

---

## Цикл

### 1. Всегда начинать от актуальной main

```bash
git switch main
git pull --ff-only origin main
```

`--ff-only` обязателен: если он падает, значит локальная `main` разошлась с удалённой, и это надо разобрать, а не заминать мержем.

### 2. Создать одну временную ветку задачи

```bash
git switch -c author/hupovoy/episode-005
```

**Схема имени:** `author/<github-логин>/<задача>`

Примеры: `author/hupovoy/episode-005`, `author/hupovoy/kolobok`, `author/hupovoy/bible-sync`.

### 3. После работы

```bash
git add <нужные файлы>
git commit -m "episode005: ..."
git push -u origin HEAD
```

`git add` только конкретных файлов — см. `commit-policy.md`. Никогда `git add .` или `git add -A`.

### 4. Создать PR строго в main

```bash
gh pr create --base main --reviewer alexeykrol
```

`--base main` указывать **явно**, даже когда main является дефолтной веткой. Явное указание защищает от того, что дефолт когда-нибудь поменяют.

---

## Ревьюер обязателен

`--reviewer alexeykrol` в каждом PR.

**Причина:** у репозитория ноль наблюдателей (`subscribers_count: 0`) — владелец не подписан. GitHub рассылает уведомления о новых PR только тем, кто нажал Watch. Без запроса на ревью автор PR остаётся единственным, кто о нём знает.

Запрос на ревью — прямое персональное уведомление: приходит письмом независимо от настроек Watch и попадает в очередь **Review requests**.

Забыли при создании — добавить следом:

```bash
gh pr edit <номер> --add-reviewer alexeykrol
```

---

## Проверка перед отправкой

Если PR создаётся через **VS Code или сайт GitHub**, а не через `gh`, перед отправкой сверить:

- **base:** `main`
- **compare:** `author/hupovoy/episode-005`

В шапке PR должно быть написано:

> into `main` from `author/hupovoy/episode-005`

⚠️ **Автоудаление веток не исправляет неверную базу.** Опция репозитория убирает накопление слитых веток, но если PR нацелен не в `main`, она об этом не сообщит. Базу проверяет человек или агент, больше некому.

---

## После merge

Удалённую ветку GitHub удаляет **автоматически** — опция включена. Локальную надо убрать руками:

```bash
git switch main
git pull --ff-only origin main
git branch -d author/hupovoy/episode-005
git fetch --prune
```

`git branch -d` (строчная) — намеренно: откажется удалять неслитую ветку. `-D` не использовать без явной причины.

## Чего больше не делать

| ❌ Устарело | ✅ Сейчас |
|---|---|
| PR в промежуточную ветку `episodes` | PR всегда напрямую в `main` |
| Долгоживущие ветки (`episode-002` как рабочая на несколько эпизодов) | Одна ветка на одну задачу, умирает вместе с PR |
| PR без ревьюера | `--reviewer alexeykrol` всегда |
| Копить работу в ветке неделями | Слить и завести новую |

**Ветка `episodes` удалена** после слияния PR #26 и больше не нужна.

## Историческое состояние (на 2026-08-03)

Старые ветки в репозитории остались от прежней схемы: они созданы или слиты до включения автоудаления либо не слиты вообще. Автоудаление работает только для веток, слитых после его включения — задним числом оно ничего не чистит.

Ветка `episode-002` — историческая рабочая, на ней жила работа по эпизодам 002–004 и весь фреймворк. Отстаёт от `main` на 7 коммитов и опережает на 54. **Разбирать её отдельно**, не тащить в новую схему.
